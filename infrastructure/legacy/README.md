# Анализ действующей (легаси) базы данных

Источник: `localhost.sql` — дамп phpMyAdmin, MySQL 8.0.25, база `u3444889_default`,
снят 21 июля 2026 г. Файл в репозиторий не включается (`.gitignore`: `*.sql`).

В каталоге хранится только обезличенная сводка справочных значений:
[`legacy-reference.json`](legacy-reference.json). Персональные данные, Discord ID,
хеши паролей и аватары в репозиторий не выгружаются.

## 1. Общая картина

Легаси-система состоит из двух несогласованных слоёв хранения.

внутри которого лежит вся предметная область:

Рядом лежат копии этого же документа: `db_test`, `db_bak_before_restore`,

### Слой 2. Реляционные таблицы (новее)

Модули дел и проверок частично вынесены в нормальные таблицы:

- `cases`, `case_comments`, `case_links`, `case_status_history`;
- `checks`, `check_participants`, `check_reports`, `check_report_files`,
  `check_interviews`, `check_interview_answers`, `check_approvals`,
  `check_gp_notes`, `check_summary_snapshots`, `checks_module_settings`;
- `faction_person_profiles` — профили сотрудников проверяемых фракций;
- `calendar_events`, `notifications`, `audit_logs`, `audit_log`, `rate_limits`.

Итого 22 таблицы. Сущностей сотрудников в реляционном слое нет — пользователи
существуют только в JSON-документе, а таблицы ссылаются на них строковым
`user_id`, без внешних ключей.

|---|---|

## 3. Открытые вопросы (требуют решения до миграции данных)

### 3.1. Роль «Прокурор субъекта»

В легаси семь ролей, в техническом задании — шесть:

| Легаси | Пользователей | ЕИАС «Фемида» |
|---|---:|---|
| Сотрудник | 144 | `EMPLOYEE` |
| Старший помощник | 14 | `SENIOR_ASSISTANT` |
| Прокурор УСБ | 0 | `USP` |
| Руководитель | 18 | `BOSS` |
| **Прокурор субъекта** | **25** | **`BOSS` (принято по умолчанию)** |
| Федеральный уровень | 9 | `FEDERAL` |
| Администратор | 2 | `ADMIN` |

«Прокурор субъекта» — руководитель округа, «Руководитель» — начальник отдела
внутри округа. Сейчас обе роли сводятся в `BOSS`, различие сохраняется только
в должности. Требуется подтверждение либо введение седьмой роли.

Обозначение `USP` соответствует роли «Прокурор УСБ» — Управление собственной
безопасности (должности `usp1`, `usp2`, группа «Управление собственной
безопасности»). Действующих пользователей с этой ролью нет.

### 3.2. Субъект «Патрики»

В данных встречается субъект `Патрики` (1 пользователь) — не приведённое к
справочнику название Патриаршего федерального округа. При миграции сводится
к `PATRIARSHY`.

### 3.3. Загрязнение справочника должностей

У части пользователей в поле `position` записан идентификатор должности
(`mmlvbstkqclsp`, `mmlvbni81e5j7`), а не название; встречаются значения
`Суворов Илья Ильич`, `Джамал`, `Помощик прокурора` (опечатка). Перед миграцией
требуется нормализация по справочнику `positions`.

## 4. Замечания по безопасности легаси-системы

Обнаружено при анализе дампа. На ЕИАС «Фемида» не переносится.

1. **Пароли в открытом виде.** В `app_state.registrationRequests` заявки хранят
   поле `password` открытым текстом (например `"password":"3894"`), 417 записей.
   В ЕИАС «Фемида» пароли не хранятся в PostgreSQL вообще — идентификация
   вынесена в Keycloak.
2. **Короткие пароли.** Встречаются четырёхсимвольные числовые пароли.
   В ЕИАС «Фемида» минимальная длина — 8 символов, обязательны буква и цифра
   (`passwordSchema` в `@femida/validation`).
3. **Отсутствие внешних ключей** между реляционными таблицами и пользователями
   из JSON-документа — ссылочная целостность не обеспечена.
4. **Отсутствие изоляции резервных копий.** Полные копии базы (включая хеши
   паролей) лежат в той же таблице, что и рабочие данные, и выгружаются вместе
   с обычным дампом.

## 5. Загрузка дампа в PostgreSQL

Дамп переносится в схему `legacy` рабочей базы, после чего разбирать его
файлом больше не нужно:

```bash
pnpm --filter @femida/api run db:import:legacy -- --reset
```

Правила преобразования MySQL → PostgreSQL и проверка целостности описаны
в разделе «Действующая (легаси) база данных» корневого
[README](../../README.md). Схема ведётся скриптом и не управляется Prisma.

Разобранный ниже подход остаётся актуальным для случаев, когда база
не поднята, — например для предварительного просмотра дампа.

## 6. Как повторить разбор без базы данных

Дамп не парсится обычными SQL-инструментами из-за строк длиной ~7 МБ.
Использованный подход:

1. Прочитать файл построчно потоком (`readline`), найти строку, начинающуюся
   с `('db', '`.
2. Снять экранирование строкового литерала MySQL: `\\` → `\`, `\"` → `"`,
   `\'` → `'`, `\n`, `\r`, `\t`, `\0`, `\Z`.
3. Передать результат в `JSON.parse`.

Ключевая деталь: `\\` должно разворачиваться **в один** обратный слеш —
иначе внутренние JSON-экранирования ломают разбор.
